# カレンダーで起こす agent runner（MVP）

## Problem

締切の準備や定期の仕事を agent に任せたくても、起動の設定は vendor ごとの cron・routines・automation に散らばっていて、人間の予定と並べて見られない。新しい仕事を足すたびに設定ファイルを書き、締切の何日前に何を始めるかは人が覚えておくことになる。

## 導出

Story「人が、自分の予定と締切を Google Calendar に書いておくと、agent がそれに合わせて準備と定期の仕事を自分で始める」の最初の一本。Core actions の3つ（期日を書く・定期の仕事を置く・実行記録と承認待ちを確かめる）をすべて通す。

## Overview

人は Google Calendar に2種類の予定を書くだけでよい。締切は記録用カレンダーに書き、準備が要るものは notes に「準備: 30日前」と1行添える。agent に任せる定期の仕事は起動用カレンダーに繰り返し予定として置き、notes の先頭に prompt を書く。runner はその時刻に Gemini の agent を起こし、締切の準備や定期の仕事をさせる。agent がカレンダーへの書き込みなど副作用のある操作をしたいときは承認待ちに入り、人が dashboard で承認して初めて実行される。

### Goals

- 締切を書いた人が、準備を始める日を自分で覚えておかなくてよくなる
- 定期の仕事の追加が「カレンダーに予定を1件置く」操作で済む
- agent が何を入力に、何を呼び、何を出したかを、人が後から確かめられる

### Non-Goals

- OAuth でカレンダーを読むこと。MVP は service account に共有されたカレンダーだけを読み、OAuth の adapter は提出後に別 branch で足す
- local の agent（Claude Code・Orca 等）を起こすこと。起動先は cloud の Gemini だけ
- 外部への通知（メール・Slack）、任意 URL の取得など、allowlist 外の tool
- 予定の即時反映（push 通知）。反映は1分ごとの取得で足りるとする
- 複数ユーザーへの提供。カレンダーの組は demo と本人の2つだけ

## Glossary

| 用語 | 意味 |
|---|---|
| 記録用カレンダー | 締切・手続きの期日を書くカレンダー（例: Agent Cal）。事実だけを書き、起動の指示は書かない |
| 起動用カレンダー | agent に任せる定期の仕事を置くカレンダー（例: Automation）。起動の正本 |
| payload | 起動用カレンダーの予定の notes 先頭に置く、agent への指示。書式は runner が決める |
| 準備期間 | 記録用カレンダーの notes の「準備: N日前」。締切の開始日から N 日前が準備の発火日 |
| 発火 | 予定に基づいて agent を1回起こすこと。同じ予定・同じ回は1度しか発火しない |
| 遅れて登録 | 予定を足した時点で発火日を過ぎていたこと。即時に発火し、そのことを agent に伝える |
| カレンダーの組 | 起動用・記録用（と、あればメイン）をまとめた単位。デモ用の demo 組と本人用の owner 組がある。カレンダー ID は設定で持つ |
| 作成者 allowlist | 組ごとに持つ、起動用カレンダーの予定を発火させてよい作成者の email の一覧 |
| 承認待ち | agent が求めた副作用のある操作。人が承認するまで実行されない |

## Domain Model

- 発火の元は2つだけ。起動用カレンダーの予定（開始時刻に発火）と、記録用カレンダーの「準備: N日前」付きの予定（開始日 − N日に発火）
- runner はカレンダーの組を複数持つ。demo 組は誰でも読み取りだけでき、owner 組は本人だけが見られる。組をまたいで予定や記録を混ぜない
- payload を命令として解釈するのは起動用カレンダーの予定だけで、さらに作成者（creator / organizer）の email がその組の allowlist にある場合に限る。メインと記録用カレンダーの title・notes は信頼しないデータとして agent に渡すだけで、命令として扱わない
- カレンダーの読み書きは adapter を通す。MVP の adapter は service account に共有されたカレンダーを読むものだけ
- payload が読めない予定は発火せず、読めなかったことを記録に残す
- 発火の検出は日付の範囲で切らない。未来の予定は全件を持ち、何か月先でも、いつ足されても拾う
- agent が使える操作は allowlist で決まる。読み取りはその場で実行し、副作用のある操作は承認待ちを経る
- agent が書き込めるのは記録用カレンダーだけ。起動用カレンダーには書き込めない（agent が自分の起動を増やせない）

## Acceptance Criteria

- 人が起動用カレンダーに payload 付きの繰り返し予定を置くと、各回の開始時刻（1分程度の遅れは許容）に agent が1回だけ起動し、dashboard に実行記録が出る
- 人が記録用カレンダーに「準備: N日前」付きの締切を書くと、開始日 − N日に agent が準備を始める。書いた時点でその日を過ぎていれば即時に始まり、遅れて登録されたことが記録に残る
- payload が読めない予定と、作成者が allowlist にない予定は発火せず、dashboard でその理由が分かる
- notes に agent への命令を紛れ込ませても、記録用カレンダーからは allowlist 外の操作も承認なしの書き込みも起きない
- agent が予定の追加を求めると承認待ちに入り、本人が dashboard で承認したときだけ同じ組の記録用カレンダーに予定が入る
- 人が dashboard で、組ごとに次の発火予定・実行記録（入力・tool 呼び出し・出力）・承認待ちを確かめられる
- 審査員がログインなしでデプロイ URL の dashboard の demo 組を読み取りだけで見られる。owner 組の予定・記録と、承認などの書き込み操作は本人の秘密 token なしでは見えず、実行できない

## Non-Functional Requirements

- Google Cloud（Cloud Run・Cloud Scheduler・Firestore）で動き、agent は Vertex AI の Gemini を service account で呼ぶ。API key を持たない
- 1分ごとの取得では LLM を呼ばない。LLM を呼ぶのは発火したときだけ
- 秘密を repo に置かない

## Success Metrics

- デモカレンダーに置いた起動用の予定と準備付きの締切が、デプロイ環境で取りこぼしなく発火し、dashboard に記録が残る
- 作者自身が Orca automation の定期実行を1本、起動用カレンダーに移して動かせる（MVP 後）
